# Architecture decision: local native sessions

The initial workspace is empty. Use a small local Node application, SQLite, readable Markdown skills, and a pseudoterminal for native agent CLIs. The server saves artifact versions, approvals, session metadata, handoffs, and terminal logs under `.workflow`. A browser connects over loopback to an interactive terminal; the installed CLI handles authentication; Claude Code is launched and resumed with `--dangerously-skip-permissions`, while Codex uses its configured permissions. The selected stage skill is included in full in the initial prompt, so both Codex and Claude Code receive the same instructions regardless of their skill discovery directories.

## Alternatives considered

- [CCManager](https://github.com/luyi256/CCManager) (MIT) offers an Express/Socket.IO server, SQLite, agent runners, browser UI, and session browsing/continuation. It is a larger multi-machine control plane; its documented surfaces do not establish the exact approval and artifact handoff contract needed here. Integrating or modifying it needs a deeper source/API assessment.
- [OpenSpec](https://github.com/Fission-AI/OpenSpec) (MIT) offers customizable spec artifacts and skills for multiple agents. It does not itself supply the requested interactive session workspace or this approval model. It could be integrated later if its artifact conventions prove useful.
- [Cezarion](https://github.com/hearsay-tools/cezarion) (MIT) offers a web cockpit, agent runners and workflow definitions. Its automated workflow execution and permission configuration would require adaptation for explicit engineer-led stage starts and this handoff model.

These are preliminary evaluations of public project READMEs and repository metadata, not a full source or security audit. No project is required as a dependency. Local native CLI help was inspected for interactive startup and Claude session IDs/resume. A PTY is a pragmatic compatibility layer, not a structured provider API: provider-specific session identification, reliable event parsing, and reconnect semantics remain future work.

## Trust and limitations

The server listens on 127.0.0.1, checks loopback Host, same-origin WebSockets and a per-process token on mutations. It has the local user's filesystem and process privileges. It is not designed for network exposure or multiple users; loopback is not an operating-system sandbox. A plan approval is not a CLI permission or organizational authorization. Claude Code permission checks are disabled for sessions launched here, so it can act with the local user’s access without prompting. Codex retains its configured permission behavior.

The terminal transcript can contain anything the agent prints, including sensitive data. Avoid entering secrets; logs and SQLite data remain local and should be protected like the checkouts. Artifact capture can be requested from an attached running session; it writes a local JSON handoff and imports it as draft versions while the browser polls. Manual editing is also available. Capture can fail if the agent cannot write the file, the session ends, or an artifact changes while capture is pending; and external discovery, PR creation and test execution depend on the selected agent, local checkout, credentials, and permissions. Claude resume is supported using a recorded native ID; Codex resume is not yet exposed because this PTY adapter does not reliably capture the native ID. Sessions interrupted by an application restart are not kept alive. Worktrees and automated cross-checkout isolation are not implemented; concurrent sessions can share registered paths; the interface shows overlapping running sessions so engineers can coordinate changes. Repository branch/commit values in the handoff are snapshots, not immutable checkout isolation.
